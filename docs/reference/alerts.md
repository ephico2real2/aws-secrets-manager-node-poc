# Alerts and notifications

[← README](../../README.md) · [Chapter 7: alerts and audit](../learn/07-alerts-and-audit.md) · [Security controls](security-controls.md)

**What this page is:** every alert and notification Secure Notes can raise. For each one
it lists what it means, what raises it, who receives it, and the first thing on-call
should do. The table is generated from `backend/src/alerts/catalogue.js`, the same list
that generates the local vmalert rules and the CloudWatch alarms. So the documentation,
the laptop and AWS can't disagree.

## How alerts travel

| | Locally (Docker Compose) | On AWS |
| --- | --- | --- |
| The app logs an `event` | stdout, plus the OpenTelemetry Collector → VictoriaLogs | journald, plus `/var/log/secure-notes/app.jsonl` → CloudWatch agent → CloudWatch Logs |
| A rule turns log lines into an alert | vmalert (LogsQL over a window) → Alertmanager | Metric filter → CloudWatch alarm |
| A secret is read by someone unexpected | AWS mock: a CloudTrail-shaped record → the stack's own EventBridge rule | CloudTrail → EventBridge rule `SecretReadAlertRule` |
| Delivery | sns-logger, the local SNS: <http://localhost:4575> | Amazon SNS |

There are three topics with the same roles on both sides. Locally they have the names below;
on AWS CloudFormation generates the names, so read the ARNs from the stack outputs
(`SecretReadAlertTopicArn`, `OpsAlertsTopicArn`, `OpsChatTopicArn`):

| Topic | Receives | Subscribers |
| --- | --- | --- |
| `secure-notes-secret-read-alert` | unexpected secret reads | email, SMS, chat |
| `secure-notes-ops-alerts` | critical app alarms, the test alert (local demo only) | email, SMS, chat |
| `secure-notes-ops-chat` | warnings, the app's own notifications | chat (email if no chat endpoint) |

Recipients are never part of the app's configuration: they are SNS subscriptions. On AWS
you set them with the stack parameters `AlertEmail`, `AlertPhone` and `AlertWebhookUrl`.
`AlertEmail` subscribes the address to each topic, so confirm **every** confirmation email.

**Behaviour worth knowing:**

- **Who gets what follows the severity.** Critical alarms page (email, SMS and chat); warnings go to chat.
- **Startup retries don't page.** While the app is starting, a failed fetch is logged at debug
  and retried. Only the final give-up, `secrets.load.fatal`, raises an alert.
- **Recovery is news, not a page.** On AWS an alarm's return to OK goes to the chat topic.
  Locally, Alertmanager sends no resolved message, because a receiver can't send "resolved"
  to a different topic than "firing".
- **Re-notify** applies locally: Alertmanager repeats a still-firing alert at most this
  often. A CloudWatch alarm notifies once per state change.
- **Windows differ slightly.** vmalert's window slides; a CloudWatch period is a fixed block.
  So "3 in 10m" can fire a little earlier locally.
- **SMS from alarms is long.** Alertmanager and CloudWatch send one text for every protocol,
  so their SMS runs to several parts. The app's own notifications carry a separate SMS text
  of at most 140 bytes.
- **The test alert** is a demo button and is limited to one a minute. Production refuses
  demo mode, so on AWS test a topic with
  `aws sns publish --topic-arn <OpsAlertsTopicArn> --message test`.

## What to do

### secret.read.unexpected

*A secret was read by an unexpected identity.* Find the identity in the alert. If it was not a planned break-glass read, rotate the secret now and review that identity's access.

### config.unsafe

*App refused to start: unsafe configuration.* Read the log line: it lists each problem (a credential in the environment, a missing secret name, a lab flag in production). Fix the unit or ConfigMap and restart.

### secrets.load.fatal

*App could not load its credentials and exited.* Check the role can reach Secrets Manager (VPC endpoint, IAM, KMS) and that the secret names resolve. The app is down until it can read them.

### secrets.fetch.failed

*A credential could not be read from Secrets Manager.* Check IAM, the VPC endpoint, KMS and the secret name in the log line. If the line says cached=true (a forced refresh failed), the app keeps serving the value it holds until that is SECRET_MAX_STALE_SECONDS old; with cached=false, requests that need this credential are failing now.

### secrets.fetch.stale

*Serving a cached credential: Secrets Manager unreachable.* The app keeps working on the last good value for up to SECRET_MAX_STALE_SECONDS. Find out why refreshes fail before that runs out.

### agent.forbidden

*The local credentials agent refused the app.* The agent answered 403: the app is not sending its SSRF token, or the token file is unreadable. Check the token file and group membership. Logged at once, even while a cached value is still served.

### db.auth.rejected

*Postgres rejected the cached password.* Usually a rotation the app recovers from by itself (look for db.auth.recovered). Repeated rejections mean the secret and the database disagree.

### cache.auth.rejected

*Redis rejected the cached password.* Usually a rotation the app recovers from by itself (look for cache.auth.recovered). Repeated rejections mean the secret and the Redis user disagree.

### cache.refresh.failed

*Redis credential refresh failed.* Redis rejected the password and the app could not read a new one. Check Secrets Manager access and the rotation function.

### secrets.reveal.enabled

*Secret values are being written to the log (lab flag on).* LOG_REVEAL_SECRETS=true is for labs. Turn it off and treat the values in this log as exposed.

### rotation.demo.failed

*A demo rotation failed.* Demo only. The log line names the step that failed.

### app.errors.burst

*Burst of errors in the app log.* Look at the error lines in the log store for the same five minutes.

### credential.rotated

*Information only.* The app read a new version of a secret and carried on. If you did not expect a rotation, check the secret's rotation schedule and CloudTrail.

### alerting.test

*Information only.* Someone pressed "Send a test alert" on the dashboard (demo mode). It proves the topic, the subscriptions and the delivery work.
